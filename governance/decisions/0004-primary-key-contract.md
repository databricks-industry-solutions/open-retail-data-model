# ADR 0004: Primary-key contract is a BIGINT identity surrogate plus a durable business key

**Status:** Accepted (2026-06-15)

## Context
Contributions arrived with two surrogate-key styles: Delta `BIGINT GENERATED ALWAYS AS IDENTITY` and ETL-generated or hash-based keys (including STRING hashes on some bridge and identity tables). A shared core needs one key contract so foreign keys, synthetic-data generation, and consumer joins are uniform.

## Decision
Every canonical-core master and dimension has a surrogate primary key, `BIGINT GENERATED ALWAYS AS IDENTITY`, named `<table>_sk`, with constraint `pk_<table>`, plus a separate durable STRING business key named `<table>_id`. `GENERATED BY DEFAULT` is permitted only for documented migration or backfill paths. STRING hash or UUID surrogates are not adopted for canonical core; if a replayable hash key is ever wanted for a gold or bridge table, that needs its own ADR.

> Superseded in part by [ADR 0011](0011-key-naming-by-grain-role.md): the `<table>_sk` / `<table>_id` form is the **default** stem, but the stem generalizes to `<stem>_sk` / `<stem>_id` naming the entity's grain/role (applied consistently), with documented exceptions (date dimension, reference-code tables, entity-split role tables, and the uniform fact-surrogate house style). The BIGINT-identity + durable-STRING contract itself is unchanged.

Foreign keys reference the parent surrogate key (`<parent>_sk`) and are named `fk_<child>_<parent>`. Business-key joins are not declared as UC foreign keys, because under SCD2 the business key is not unique.

## Consequences
- One uniform key shape across the core, so generators and consumers do not special-case per table.
- Keys generated on extraction from contributions that used a different style (for example ETL-BIGINT or hash keys) are converted to the IDENTITY contract.
- Note the IDENTITY concurrency caveat: `GENERATED ALWAYS` disables concurrent transactions, so it is reserved for masters, dimensions, and moderate-volume facts, which is a further reason the durable business key stays a separate column.
